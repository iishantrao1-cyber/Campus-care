1. Problem & solution

Colleges need accountable grievance redressal: hostel, mess, academics, IT, transport, and ragging issues often disappear into WhatsApp threads or offline suggestion boxes. UGC/AICTE expectations require a working grievance cell with traceability.

Campus Care turns each issue into a ticket with a public ID, status timeline, department routing, verified student/staff identity (college directory + email OTP), and an admin control room — without allowing self-registered administrators.

3. Architecture

Browser  --HTTPS-->  Next.js (Server Components + Server Actions)
                              |
                         Drizzle ORM
                              |
                         PostgreSQL
                         (users, directories, complaints, OTP, outbox)
                              |
                      SMTP gateway (optional)
                      else admin-only email outbox

Mutations run in "use server" actions. The browser never receives database passwords, session secrets, or the authority to set role=admin.

email_verificationsHashed OTPs for register/reset
email_outboxMail audit; OTP holding for IT if no SMTP
complaintsTickets, status, assignment, anonymity
complaint_updatesTimeline / audit trail

Status flow: submitted → under_review → in_progress → resolved → closed (or rejected).

5. Step-by-step build

Phase A — Scaffold

npx create-next-app@latest campus-care --typescript --tailwind --app
cd campus-care
npm install drizzle-orm pg dotenv
npm install -D drizzle-kit @types/pg

Phase B — Database client & schema

  1. Create src/db/index.ts with a pg Pool and drizzle(pool).
  2. Define tables in src/db/schema.ts.
  3. Add drizzle.config.json pointing at the schema and DATABASE_URL.
  4. Run npx drizzle-kit push.

Phase C — Auth library

  1. scrypt password hash/verify
  2. HMAC-signed httpOnly session cookie
  3. Login & OTP rate limits
  4. Email challenge create/consume
  5. TOTP MFA helpers

Phase D — Server Actions

  • auth.ts — login, register student/staff, verify OTP, reset password
  • admin-directory.ts — CSV import, provision admin, activate users
  • complaints.ts — create/update/feedback with authorization

Phase E — Pages & UI

Home, register, verify, login, dashboard, new complaint, ticket detail, public track, admin queue, admin directory. Keep existing Campus Care forest/cream styling; only add auth fields (OTP, MFA, directory empty state).

Phase F — Validate

npx next typegen
npx tsc --noEmit
npm run build
npm run start

6. Auth, OTP & MFA

Student / staff verification

  1. User submits college ID + official email + password.
  2. Server checks active directory row: ID and email must match.
  3. Domain-only checks are insufficient and not used as sole proof.
  4. OTP emailed (or placed in admin outbox).
  5. On success, account created with server-assigned role only.
If the authorized directory has zero rows, registration UI shows “unavailable” — open signup is blocked on purpose.

Admin

  • Created via ADMIN_BOOTSTRAP_* env (first time) or existing admin provision form.
  • Login requires MFA (TOTP / backup codes).
  • Public registration cannot create admins.

7. Roles & authorization

RoleAllowedDenied
Student Own complaints, feedback, public track Other students’ tickets, /admin
Staff Assigned / same-department tickets Directory admin tools, unrestricted all-campus unless assigned
Admin Full queue, assign, directory, provision admins Self-signup as admin

IDOR rule: loading /complaints/124 always checks ownership or staff scope on the server.

8. Complaint workflow

  1. Verified student files ticket (category → department).
  2. System assigns ticket number like CC-2026-0001.
  3. Timeline logs every status change.
  4. Staff/admin updates status and notes.
  5. Student rates resolution; ticket may close.
  6. Anyone can track by ticket ID on /track (anonymous names hidden).

9. Security checklist

  • Password hashing (scrypt) — no plain text
  • Rate-limited login & OTP
  • httpOnly, Secure (prod), SameSite=Lax cookies
  • Parameterized SQL via Drizzle
  • XSS escaping of user content
  • Server-side RBAC on every action
  • Secrets only in environment variables
  • .env gitignored
  • HTTPS in production
  • No public demo credentials on marketing pages

10. Environment & deploy

DATABASE_URL=postgresql://...
SESSION_SECRET=long-random-string
APP_URL=https://campuscare.college.edu
ADMIN_BOOTSTRAP_EMAIL=...
ADMIN_BOOTSTRAP_PASSWORD=...
ADMIN_BOOTSTRAP_NAME=...
ADMIN_BOOTSTRAP_EMPLOYEE_ID=ADM-001
# optional SMTP_* and ADMIN_MFA_BOOTSTRAP_CODE
  1. Provision Postgres and set env.
  2. drizzle-kit push then npm run build && npm run start.
  3. Terminate TLS at reverse proxy.
  4. Admin imports student/staff directories.
  5. Configure SMTP; rotate bootstrap secrets.

What college IT must provide

  • Authorized student list (ID, name, official email, dept, course, year, active)
  • Authorized staff list (employee ID, name, email, dept, designation, active)
  • SMTP or mail relay
  • First admin identity
  • Production domain + HTTPS certificate
